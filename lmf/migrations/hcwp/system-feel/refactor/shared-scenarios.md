## Boundary projections and adaptations

- **Summary:** compare every current `PatientSummary` field to the corresponding approved reference field: full name, NHS number, date of birth, displayed age, address, school, organisation, alert visibility/text, sex and current status code. Sex comes from the reference enum request's numeric argument; status comes from its resolver request argument. The repository receives the unchanged selected-ID and supplied navigation graphs, including other-patient rows.
- Resource prose is still unavailable. Symbolic school resource objects remain symbolic. Current status/sex descriptions, age-label/date-label markup, child/status dialog resource calls, EF6 Include tracking and excluded DefaultAccess calls are not invented in the application observation. These reference outputs remain retained in full, but are not claimed as integrated infrastructure. Age display is compared, including status `7`; computed-but-hidden `AgeString` is not falsely compared to a visible value.
- **Name/address/age helper scenarios:** unchanged inputs are wrapped in a minimal synthetic summary repository graph with client 101, empty optional collections and a controlled clock, then executed through `PatientSummaryQuery.Read`, not directly against converted helper methods. Only the corresponding result field is projected to the approved protocol. Ancillary defaults are not observations or expectations.
- **Results:** approved flattened rows are mapped to the existing EF InMemory entities, committed and retrieved through `Kd03ResultsQuery.Search`; each returned key is read again through patient-safe `Detail`. All fields in the approved row protocol are observed from the retrieved DTO. No expected row is returned as an observation. Search size 50 avoids truncating the approved 23-row history; paging semantics remain separately tested.
- The reference has flattened navigation values, not consistent global lookup tables: its foreign-patient sentinel deliberately reuses location/examiner codes with different names. Dependency doubles prioritize requested-patient navigation values for those codes. This is an explicit synthetic graph adaptation, not proof of a production lookup schema. `SyntheticNonKdp` is represented by the non-KDP `OtherScreening` enum, preserving the source query's KDP/non-KDP predicate. `ExamType` in returned rows is the boundary invariant KDP, not a persisted DTO property.
- The recording mapper joins examiner name parts with a space. The adapter represents the supplied complete name as Name1 with empty Name2 and strips only that join's trailing whitespace for comparison. It does not trim patient names or addresses. The existing recording DTO's absent measurement key sentinel `0` is normalized to reference `null` on both sides; no clinical measurement is changed. Raw observations retain `0`.
- **Equal-date ordering:** raw outputs retain the approved Refactor recorded-date/ID descending tie-break. For parity only, complete rows are canonicalized by contact date descending then ID ascending on all sides, preserving all field values and row multiplicity. The unchanged approved date-group and ID-multiset expectations are also checked against raw application output; they prove date order, cardinality and patient isolation without asserting a source tie-break. Separate query tests assert the target's actual deterministic tie order and paging. No reference tie-break is inferred.
- **SF-037:** the approved source scenario intentionally retrieves all KDP contacts. The application is deliberately KD03-only. Reference and Convert must first satisfy the original complete approved expectation; their complete rows are then projected to KD03. The application expectation retains exactly the approved ID multiset intersected with input KD03 rows, adds excluded non-KD03 IDs, and compares all projected row fields. The approved scenario is not edited, nor is all-KDP application parity claimed.
